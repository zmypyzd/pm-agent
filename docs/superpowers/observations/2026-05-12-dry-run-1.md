## Issues observed

### **[High]** PR-recording: UNIQUE constraint on `prs.github_number` when `gh pr create` fails

When `gh pr create` returns a non-zero exit (no remote here; in real
deploys: auth expired, rate limit, branch protection), `open_pr` returns
`PRResult(number=0, url="", action="failed")`. The cycle loop then calls
`persistence.record_pr(... github_number=0 ...)`. The first failed PR
inserts successfully; the second hits
`sqlite3.IntegrityError: UNIQUE constraint failed: prs.github_number`
and the finding is marked failed.

Across 3 cycles this bug fired **at least 5 times**: findings `53185efb`,
`a99d8b23` (cycle 1), `9ed95842`, `c03057f7` (cycle 2), `9ed95842`
(cycle 3 — same bug re-found, failed again, will skip in cycle 4 when
attempt count hits 3). Cycles 2 and 3 fixed **0 findings** in part because
of this — every promising fix attempt died at the `record_pr` step.

Evidence: every `loop.log` ERROR line in the run has the same trace
through `pm_agent/loop.py:343` → `pm_agent/persistence.py:209` with
`IntegrityError: UNIQUE constraint failed: prs.github_number`.

Severity rationale: High because **any** real cycle that creates ≥2
PRs which fail to land (auth expired, branch protection mid-cycle) will
hit this. Not just no-remote dry-runs.

Fix sketch: either (a) make `github_number` nullable + drop UNIQUE
when 0/null, or (b) skip `record_pr` entirely when
`PRResult.action == "failed"` (cleaner — failed creates carry no
durable PR identity).

### **[Medium]** `pm-agent loop report` coder cost is always N/A

`pm_agent/report.py:160` reads `cost_map.get("coder")`, but the cycle
loop writes per-coder cost rows with `agent="coder-1"` / `"coder-2"`
(`pm_agent/loop.py` `_drive_coder` callers). No row ever has
`agent="coder"`, so `cost_coder` is always None.

Evidence: report output shows `coder: N/A` and `total: $0.09` while
`cycles.cost_usd = 3.6414` and the costs table sums to $3.64. The two
disagreements have the same root cause.

Fix sketch: in `report.py`, sum costs where
`agent LIKE 'coder%'` (or split into `coder-1` / `coder-2` lines if you
want per-coder breakdown). Same patch needs to flow into the dashboard
cumulative banner if it uses the same code path.

Severity rationale: Medium not High because the data is correct in
`costs` and `cycles.cost_usd`; the bug is only in the operator-facing
aggregation. Mentors looking at `loop report` will however see
"\$0.09 for 4 cycles" and conclude the daemon does nothing.

## What dry-run #1 told us about the Beta loop

- **Cancellation safety holds.** Auto-stop at 17:57 produced 0 cycles in
  `running` state. The R3 `_ensure_finished` closure (commit `044a44c`)
  worked exactly as designed when SIGTERM landed during an inter-cycle
  sleep.
- **Per-finding isolation works.** The PR-recording crash never propagated
  past the finding it hit; subsequent findings continued processing
  within the same cycle. The catch at `loop.py:349` ("finding %s raised
  unexpected exception; marking failed") is doing its job.
- **The "3-attempts then skip" gate works.** Bug `9ed95842` was found in
  cycles 1, 2, and 3 (same bug_id rehydrated each scan) and the
  `fix_attempts >= 3` check would skip it on a hypothetical cycle 4.
- **Scanner is reproducible enough.** 5 findings/cycle across 3 cycles
  with significant overlap on bug_id values — the scanner is not
  generating noise that drifts every cycle.
- **PR-creation failure path is undertested.** The fact that two
  net-new High/Medium bugs landed in the very first cycle (both in
  the failed-PR code path) means the test suite did not have
  realistic coverage of the "gh pr create returns non-zero" branch.
  R4 fix wave should add an integration-level test with a stubbed
  `_gh` that returns rc=1.
