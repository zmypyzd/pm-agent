## What dry-run #3 told us

- **Push step works.** Every integration branch reached the remote;
  `gh pr create` then succeeded for 3 of 11 findings. The 8 that
  failed died at earlier gates (NO_CHANGES, gates_failed, or
  conflicts), not at push or at PR-create.
- **Cycle 2 was a near-no-op** ($0.08, 21s, scanner found 1 finding,
  Coder-1 returned NO_CHANGES). Pure Claude variance — the scanner is
  LLM-based and occasionally returns short batches. The loop handled
  it cleanly: 1 finding marked failed, no spend escalation, no zombie.
- **Auto-merge never fired.** Three PRs opened, zero auto-merged. The
  loop *did* call `gh pr merge --auto --squash` (Low severity +
  gates_green → `auto_merge` route), but on a fresh GitHub repo with
  no branch protection / no required-checks, gh's auto-merge has
  nothing to "wait for" and doesn't queue. This is a new repo
  ergonomics question, not a loop bug. See action items.
- **Same `bug_id` across cycles produces separate PRs.** The scanner
  re-found `35a1d02f` in cycles 1 and 3; both produced distinct PRs
  (head branches `cycle-1-...` vs `cycle-3-...`). `open_pr` is
  idempotent *per head branch*, not *per bug_id* — a future improvement
  would be to look up bug_id and close older PRs or reuse the branch.
- **Cost dropped 63% vs D2** ($12.24 → $4.59). Same code path but
  more findings exit the per-finding pipeline at gates earlier when
  there's a real success outcome possible — the loop is no longer
  pushing every finding all the way through Coder-2 + integration
  before failing at PR-create. This pattern is what real production
  cost will look like.

## Issues observed

None blocking. Two ergonomic follow-ups (low priority, file but don't
fix this session):

- **Issue R5-1 (Low)**: `auto_merge` doesn't visibly distinguish "queued
  successfully" from "no auto-merge possible" on a fresh repo. With
  no branch protection, `gh pr merge --auto` may exit 0 without
  actually enabling auto-merge. The PR shows OPEN. Future surfacing:
  log "auto-merge queued vs declined" instead of just relying on the
  PR state to indicate the outcome.
- **Issue R5-2 (Low)**: Same `bug_id` re-found in a later cycle creates
  a duplicate PR rather than updating/replacing the prior one. Not a
  bug, but inefficient on long runs.
